固件变体与 OTA 小白教程

先看结论：不知道该选什么，就选“标准版”；变体不是越多越好。

一、先分清三种“内存”

名称通俗理解断电后主要用途
芯片内部 RAM书桌，速度快但空间有限内容消失程序运行、变量、网络缓冲
SPIRAM / PSRAM外接的大书桌内容消失扩大可用堆，容纳图片、数组、网络数据
Flash硬盘/书柜内容保留固件、Python 文件、配置和文件系统

所以：选择 SPIRAM 不会把 4MB Flash 变成 8MB，也不会自动增加存储空间；它只对确实焊有 PSRAM 的硬件有意义。

二、每个变体到底是什么

标准版

使用开发板默认配置。适合普通 ESP32-WROOM、没有特殊分区需求的设备，也是小白首选。

SPIRAM / PSRAM

给带 Quad-SPI PSRAM 的 ESP32 使用，常见于 WROVER 模组。启用后 MicroPython 可以把更多动态内存分配到外部 RAM。

板上没有 PSRAM时不要选。

Octal-SPIRAM

给明确配备 Octal（八线）PSRAM 的 ESP32-S3 使用。它和普通 Quad PSRAM 的硬件连接模式不同，不能凭感觉选择。

规格没有明确写 Octal PSRAM，就保持标准版。

OTA

OTA 是 Over-The-Air，即“通过网络升级固件”。该变体建立两个应用分区，让新旧固件可以轮换。

它只提供 OTA 基础结构，不等于已经有一套自动升级服务。

D2WD

专用于 ESP32-D2WD 芯片，其封装内集成 2MB Flash。它不是普通 WROOM 的“2MB 选项”。

UNICORE

让 ESP32 只使用一个 CPU 核心，面向少数单核硬件和特殊兼容场景。普通双核开发板无需选择。

三、OTA 的原理

普通固件通常只有一个应用区。正在运行时如果直接覆盖它，断电或下载失败就可能无法启动。OTA 固件把 4MB Flash 主要分为：

分区大小作用
ota_0普通 ESP32：0x180000；C3 扩展：0x1A0000运行固件 A
ota_1普通 ESP32：0x180000；C3 扩展：0x1A0000备用/新固件 B
otadata8KiB记录下一次从哪个应用分区启动
vfs普通 ESP32：约 960KiB；C3 扩展：约 704KiB保存设备上的 Python 文件和普通数据

设备运行 A 时，把 B 写入另一个分区；写完并校验成功后，修改启动标记并重启。若新固件第一次启动失败，bootloader 可以回到旧固件。

本平台对普通 ESP32 OTA 和 C3 OTA 都显式启用 CONFIG_BOOTLOADER_APP_ROLLBACK_ENABLE=y。因此“新固件自检后确认、确认前异常则自动回滚”不是纸面流程，而是实际进入编译配置。

设备运行
ota_0 / 旧固件
→
下载并校验
写入 ota_1
→
切换启动并重启
确认或回滚

四、在本平台如何使用 OTA

第 1 步：编译并首次串口烧录

  1. 普通 ESP32 选择 ESP32 → ESP32_GENERIC → OTA；C3 选择 ESP32-C3 → ESP32_GENERIC_C3 → OTA（平台扩展，已验证）。
  2. Flash 保持“自动/开发板默认”，上传你的 Python 文件并创建编译任务。
  3. 第一次安装时，下载的 firmware-ota-package.zip 中有两个文件。
  4. 使用 USB/串口烧录完整的 firmware.bin。这是必须步骤，因为它包含 bootloader 和 OTA 分区表。

Windows 示例（把 COM3 换成设备端口）：

# 普通 ESP32：完整固件从 0x1000 写入
python -m esptool --chip esp32 --port COM3 erase_flash
python -m esptool --chip esp32 --port COM3 --baud 460800 write_flash -z 0x1000 firmware.bin

# ESP32-C3：完整固件从 0x0 写入
python -m esptool --chip esp32c3 --port COM3 erase_flash
python -m esptool --chip esp32c3 --port COM3 --baud 460800 write_flash -z 0x0 firmware.bin

第 2 步：下载完整示例代码

三个文件均带详细中文注释。下载后把 ota_main.py 改名为设备上的 main.py。

下载 ota_updater.py 下载 ota_boot.py 下载 ota_main.py

第 3 步：取得更新地址、大小和 SHA-256

假设已编译固件 ID 是 4，浏览器打开：

http://树莓派IP:9001/api/ota/4/manifest

把返回的 download_path、size、sha256 填入 ota_main.py。应用镜像直接下载地址格式为：

http://树莓派IP:9001/api/ota/4/application.bin

第 4 步：先测试业务，再触发升级

  1. 填写 Wi-Fi、更新 URL、SHA-256 和文件大小；先保持 START_UPDATE=False。
  2. 上传三个 Python 文件，确认设备能正常联网和运行。
  3. 准备升级时把 START_UPDATE=True，运行一次；代码会流式写入未运行的 OTA 分区。
  4. 只有长度和 SHA-256 都正确才会调用 set_boot() 并硬重启。
  5. 新固件完成 Wi-Fi 和业务自检后调用 confirm_ota()；失败则切回旧分区。
  6. 新固件中的 START_UPDATE 应恢复为 False，避免每次启动重复更新。

完整代码（可直接展开查看）

ota_updater.py：流式下载、分区写入、长度与 SHA-256 校验 
{{ ota_updater_code }}
ota_boot.py：新固件确认与主动回滚 
{{ ota_boot_code }}
ota_main.py：Wi-Fi、自检和触发升级的完整示例 
{{ ota_main_code }}

安全边界：示例会校验可信 SHA-256，并且写完前不会切换启动分区。正式公网产品还应增加设备身份认证、证书固定或数字签名；不要把密码直接放在公开 URL 中。

绝对不要：把完整 firmware.bin 写进 ota_0/ota_1。OTA 应用分区只能写压缩包里的 ota-application.bin。

六、OTA 上线前检查清单

  • 新旧固件使用相同开发板和 OTA 分区表，应用镜像不得超过 manifest/分区表容量；
  • 只允许 HTTPS，并校验 SHA-256；正式产品还应验证数字签名；
  • 把版本号、目标芯片、文件长度和哈希放在受信任的升级清单中；
  • 写备用分区期间不要切换启动，供电不足时宁可保留旧版本；
  • 新固件先完成 Wi-Fi、文件系统和核心业务自检，再确认取消回滚；
  • 保留 USB/串口救砖方式，并先在测试板完成断电、坏包和回滚测试。
